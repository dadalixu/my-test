## 新建：job_agent（LangGraph 求职助手）

按需求「1 记住找过的工作 / 2 能交互 / 3 用 langgraph」搭建，位于 `my_project/job_agent/`。

**文件清单**
- `config.py` — 读环境变量 / `.env`（自写解析器，不依赖 python-dotenv）；无 Key 自动切离线模型
- `store.py` — SQLite 长期记忆：`jobs`（fingerprint 去重 + seen_count）/ `events`（时间线）/ `profile`（偏好）
- `tools.py` — 9 个 `@tool`：search_jobs、save_job、list_jobs、get_job_detail、update_job_status、search_saved_jobs、job_stats、remember、recall_all

**关键设计决策**

- 真实端到端：系统中已有 `DEEPSEEK_API_KEY`，用真实 DeepSeek 跑通了「搜岗位→入库→列表→改状态→统计」全链路

## 追加：修复「运行不了」（当天下午）

用户反馈"我运行不了"。排查发现**代码没错，是入口设计有缺陷**：
包内用相对导入，导致只有从项目根目录 `python -m job_agent` 能跑。复现出三种失败：

| 跑法 | 报错 |
|---|---|
| IDE 里对 `job_agent/__main__.py` 点运行 | `ImportError: attempted relative import with no known parent package` |
| IDE 里对 `job_agent/cli.py` 点运行 | 同上 |
| 先 cd 进 `job_agent/` 再 `-m job_agent` | `No module named job_agent` |
| 用系统 python（非 `.venv`）跑 | `ModuleNotFoundError: No module named 'langchain_core'` |

**修法**：
1. `cli.py` / `__main__.py` / `selftest.py` 顶部（`from __future__` 之后、
   任何相对导入之前）加 PEP 366 自救块：`if __package__ in (None, ""):` → 用
   `Path(__file__).resolve().parent.parent` 注入 sys.path（**不依赖 cwd**），
   再 `__package__ = "job_agent"`，之后相对导入正常解析。
2. 新增根目录 `启动.bat`（双击即用）：`chcp 65001 >nul` + `cd /d "%~dp0"` +
   `.venv` 解释器 + `pause`。**内容全 ASCII**——cmd 按代码页逐行读 bat，
   UTF-8 中文会乱码甚至破坏命令解析。
3. README 新增「三种启动方式」+「启动不了排查表」（症状→原因→解决）。

**验证矩阵（8 种跑法全通）**：`-m job_agent` / 直接跑 `__main__.py` / 直接跑 `cli.py` /
从 `C:\` 用绝对路径跑 `cli.py` / `-m job_agent.selftest` / 直接跑 `selftest.py` /
`-m job_agent.config` / 直接跑 `config.py`；外加从 `C:\` 调用 `启动.bat`（自动切目录、中文不乱码）。
自测仍 **58/58**。

**教训**：交付带包结构的 CLI 项目前，必须把「5 种启动方式」挨个实测。
`python -m` 能跑 ≠ 用户能跑——用户会点绿三角、会双击、会 cd 错目录。

## 追加：真正定位「还是运行不了」→ 解释器自愈

问用户「怎么启动的 / 屏幕上什么反应」后拿到关键信息：
**在 IDE 里点运行按钮**，报
`[致命错误] 图构建失败：ModuleNotFoundError: No module named 'langchain_openai'`。

**根因**：IDE 点运行时用的解释器是**系统 Python**，不是项目的 `.venv`；
依赖只装在 `.venv` 里。（能报出我写的 `[致命错误] 图构建失败` 这句，
说明包路径自救已生效、代码确实跑起来了，只是卡在缺依赖。）
另外实测发现本机 `py` 启动器**找不到任何 Python**——
`py -0` 返回 "No Installed Pythons Found!"，因为用户装的是**微软商店版**，py launcher 不认它。

**修法：解释器自愈**。在 `cli.py` / `selftest.py` 顶部（PEP 366 自救块之后、
**任何第三方导入之前**）加 `_relaunch_with_venv()`：检测 `sys.executable` 是否等于
`.venv\Scripts\python.exe`，不是就用 `os.execv` 原地替换成 `.venv` 的解释器重新跑自己。
- 用 `os.execv` 而非 `subprocess`：进程原地替换，stdin/stdout 全继承，IDE 控制台仍可输入
- 用环境变量 `JOB_AGENT_RELAUNCHED=1` 防死循环
- 换不成就 `return`，让正常报错提示接手
- 副作用：Debug 模式会断开调试器，已在 README 注明"要调试请手动选解释器"

**为什么不靠 IDE 配置**：VSCode 的 `python.defaultInterpreterPath` 只在用户
**没手动选过**解释器时生效，选过之后会被用户级设置覆盖（项目里 `.vscode/settings.json`
其实早就指向 `.venv` 了，但没起作用）。所以让代码自救比教用户翻菜单可靠。

**验证矩阵（全通过）**：
- 商店版 python 跑 `cli.py`（**完整复现用户场景**）→ 自动切 `.venv` 并正常启动
- 无依赖解释器跑 `__main__.py` / `-m job_agent` / `selftest.py` → 全部正常
- `.venv` 正常路径 `-m job_agent.selftest` / `job_agent/cli.py` → 63/63，未被自愈干扰

**经验**：用户说"运行不了"时，问「你点了什么 / 屏幕上什么反应」比问「你怎么运行的」
有效得多——报错原文一句话就定位了，之前两轮全靠猜。

## 追加：修「可以运行但是不能输入」→ 放弃 execv，改「借用包目录」

用户反馈"可以运行但是不能输入"。追查发现**上一轮的 execv 自愈方案自己造了这个坑**：
`os.execv` 替换进程会让 IDE 收不到键盘输入（VSCode 调试控制台尤其明显）。

**另外查到一条关键事实**：用户 VSCode 打开的**工作区是 `my_project\job_agent`（子目录）**，
不是 `my_project` —— 所以 `my_project/.vscode/settings.json` 里指定的解释器
**根本没被读取**，这才是他一开始 `ModuleNotFoundError` 的真正原因。
（workspaceStorage 里的 `workspace.json` 记录了这个路径。）

**新方案：`_bootstrap_deps()` 三层顺序**
1. 当前已是 `.venv` 的解释器 → 什么都不做
2. **版本一致 → 直接把 `.venv\Lib\site-packages` 挂到 `sys.path` 最前面**（`importlib.invalidate_caches()`）。
   **不换进程**，IDE 输入输出、调试器连接全部完好 ← 主路径
3. 版本不一致（跨大版本加载 C 扩展会崩）→ 才退回 `os.execv` 兜底

版本一致性靠读 `.venv/pyvenv.cfg` 的 `version = 3.12.10` 比对主次版本号（`parts[:2]`）。
本机 `.venv` 与系统 Python **都是 3.12.10**，所以用户场景正好走的是第 2 条（最温和的那条）。

**配套加了两个 IDE 配置**：
- `job_agent/.vscode/settings.json` → 解释器指向 `${workspaceFolder}\..\.venv\Scripts\python.exe`
  （因为用户的工作区根是 `job_agent`，外层那份不生效）
- `job_agent/.vscode/launch.json` → F5 调试用，`console: integratedTerminal`
  （默认 `internalConsole` **不支持键盘输入**，会导致"又能跑又不能输入"复现）

**验证判据**：用商店版 3.12.10 跑 `cli.py`，看 banner 的「解释器」行**仍是系统路径**
（证明没换进程），同时 `/stats` 输入被读到并执行 —— 两条都满足才算过。
另外测了 3.13 跨版本兜底、商店版跑 `selftest.py`、`.venv` 正常路径，全部 63/63。
